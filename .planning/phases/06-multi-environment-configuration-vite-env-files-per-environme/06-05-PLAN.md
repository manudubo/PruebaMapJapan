Output: `mappers.tf` file that TF can apply to adopt the existing mappers or create them on a fresh KC instance.

```hcl
resource "keycloak_openid_user_property_protocol_mapper" "profile_username" {
  realm_id        = keycloak_realm.japan_trip.id
  client_scope_id = data.keycloak_openid_client_scope.profile.id
  name            = "username"
  user_property   = "username"
  claim_name      = "preferred_username"
  claim_value_type = "String"
  add_to_id_token     = true
  add_to_access_token = true
  add_to_userinfo     = true
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| avatar_url + preferences claims → access token | Custom user attributes are emitted in tokens; any user with a manipulated KC profile can inject arbitrary claim values |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-05-01 | Tampering | avatar_url / preferences user attribute values | accept | These are user-controlled string attributes; the frontend uses them for display only (avatar image URL, preferences blob); no authorization decisions are made based on these claims; low risk |
| T-06-05-02 | Information Disclosure | email_verified claim in access token | accept | email_verified is a standard OIDC claim; KC sets it based on email verification flow; it is expected in the token and used by the backend to check verification status |
</threat_model>
