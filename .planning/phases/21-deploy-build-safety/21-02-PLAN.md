```yaml
  test: ["CMD", "bash", "-c", "exec 3<>/dev/tcp/127.0.0.1/8080 && printf 'GET /realms/japan-trip HTTP/1.1\\r\\nHost: localhost\\r\\nConnection: close\\r\\n\\r\\n' >&3 && head -1 <&3 | grep -q 200"]
```

Why `["CMD", "bash", "-c", ...]` not `["CMD-SHELL", ...]`:
- `CMD-SHELL` invokes `/bin/sh -c`. While Keycloak 26.x (Red Hat UBI) typically symlinks `/bin/sh` → bash, using `["CMD", "bash", "-c", ...]` makes the shell explicit and eliminates ambiguity. `/dev/tcp` is a bash builtin not available in dash/ash.
- D-07 specified `wget -q --spider http://localhost:8080/health/ready` — both elements were unimplementable: `wget` is absent from the container (verified); `/health/ready` returns 404 without `KC_HEALTH_ENABLED=true` (verified). This replacement preserves D-07's intent (check KC readiness) with a verified-working method. Per 21-RESEARCH.md INFRA-05 deviation section.

Why this command works (all elements verified in live container per 21-RESEARCH.md):
- `exec 3<>/dev/tcp/127.0.0.1/8080` — opens TCP connection to KC on port 8080 using file descriptor 3
- `printf 'GET /realms/japan-trip HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' >&3` — sends minimal HTTP/1.1 GET request (note: `\\r\\n` in YAML double-quoted string becomes literal `\r\n` bash expands to CRLF)
- `head -1 <&3 | grep -q 200` — reads first response line; exits 0 only if it contains "200" (the realm endpoint returns 200 after KC has started AND imported the `realm-export.json`)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions `workflow_run` trigger | Triggered by another workflow; exposes target-repo secrets to the triggered workflow |
| CI-validated SHA → deploy | The commit that CI validates must be the exact commit deployed |
| KC Docker healthcheck | Healthcheck command runs inside the container with container-level trust |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-02-01 | Elevation of Privilege | workflow_run + CLOUDFLARE_API_TOKEN / GitHub Pages secrets exposure | mitigate | `branches: [main]` filter in `workflow_run` ensures deploy workflows only trigger for main-branch CI conclusions; no fork PR can trigger a deploy (fork PRs generate CI runs on the fork, not target repo) |
| T-21-02-02 | Tampering | Deploying wrong SHA (CI-validated commit vs default-branch HEAD divergence) | mitigate | `ref: ${{ github.event.workflow_run.head_sha }}` on both checkout steps guarantees the deployed artifact matches the SHA CI validated; without this, rapid pushes can deploy unvalidated code |
| T-21-02-03 | Denial of Service | e2e `continue-on-error: true` weakens the CI gate | accept | The e2e job has a 100% historical failure rate since April 2026 (ARCH-09); excluding it from blocking is deliberate and time-bounded — Phase 24 removes `continue-on-error` once the job is fixed; all other jobs (typecheck-frontend, typecheck-backend, test-frontend, test-backend, build-backend) block normally |
| T-21-02-04 | Tampering | KC healthcheck using /dev/tcp bash builtin | accept | The healthcheck only checks whether `/realms/japan-trip` responds 200 — it does not transmit credentials or data; bash /dev/tcp is available in the KC 26.x UBI image; CMD ["bash", "-c", ...] makes the shell explicit |
| T-21-02-05 | Spoofing | Arbitrary wrangler version via `npx wrangler deploy` | mitigate | `npm run deploy --workspace=backend` uses the installed devDep wrangler (^3.101.0 = currently 3.114.17) rather than the npm-latest resolved by `npx` at deploy time; npm ci before the deploy step installs the pinned version |
</threat_model>
