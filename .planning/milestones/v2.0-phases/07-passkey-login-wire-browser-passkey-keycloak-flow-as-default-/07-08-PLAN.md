  <action>
Run the Admin API smoke test to verify the japan-trip-worker client can authenticate against local Keycloak:

```bash
curl -s -X POST http://localhost:8080/realms/japan-trip/protocol/openid-connect/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=japan-trip-worker" \
  -d "client_secret=<value-from-KC_ADMIN_CLIENT_SECRET-in-.dev.vars>" \
  | jq '.access_token'
```

Replace `<value-from-KC_ADMIN_CLIENT_SECRET-in-.dev.vars>` with the actual value from .dev.vars.

Expected output: a long JWT string (not null, not an error object).

If the response is `{"error":"unauthorized_client",...}` — the client secret in .dev.vars does not match the KC state. Re-run `terraform -chdir=terraform/keycloak output -raw worker_client_secret` and update .dev.vars.

If the response contains `"access_token": null` — the client exists but service accounts may not be enabled. Verify Plan 07-03 Task 2 set `service_accounts_enabled = true`.

After confirming access_token is present, also verify the token has the manage-users scope by decoding it:
```bash
curl -s -X POST http://localhost:8080/realms/japan-trip/protocol/openid-connect/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=japan-trip-worker" \
  -d "client_secret=<secret>" \
  | jq '.access_token' -r | cut -d. -f2 | base64 -d 2>/dev/null | jq '.resource_access'
```
Expected: `resource_access` contains `{"realm-management": {"roles": ["manage-users"]}}` or similar.
